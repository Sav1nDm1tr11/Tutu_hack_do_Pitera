## P0-1. `/api/plan` возвращает пустой поток (оба режима)

**Где:** `apps/api/src/http/routes/plan-routes.ts:52`

```ts
request.raw.on('close', onClose);   // ← срабатывает сразу
```

**Что происходит.** В Node ≥16 `IncomingMessage` эмитит `close`, как только тело
запроса полностью прочитано, а не когда ушёл клиент. Fastify читает тело до
хендлера, поэтому `clientGone` становится `true` до первой итерации, и цикл

```ts
for await (const event of ...) { if (clientGone) break; reply.raw.write(...) }
```

прерывается **до первой записи**. Ответ: `200`, `content-type: application/x-ndjson`,
тело — 0 байт.

**Воспроизведение (чистый `main`):**

```bash
curl -s -X POST http://127.0.0.1:3001/api/plan -H 'Content-Type: application/json' --data-binary @req.json | wc -c
# 0
```

Подтверждено инструментированием: обработчик `close` вызывается сразу
(`RAW_CLOSE_FIRED` в логе), `responseTime` ≈ 1–5 мс.

**Почему не поймали тесты.** `plan-routes.test.ts` использует `app.inject()`,
который не эмитит `close` на сыром сокете. Тесты зелёные, продукт мёртвый.

**Исправление (проверено):**

```ts
reply.raw.on('close', onClose);   // и симметрично .off() в finally
```

После правки поток отдаёт все 8 событий: `plan.started` → 6 × `plan.progress` →
`plan.ready`.

### Исправлено

Коммит «Чиню обрыв NDJSON-потока /api/plan на первой итерации».

- `apps/api/src/http/routes/plan-routes.ts`: подписка перенесена с
  `request.raw.on('close')` на `reply.raw.on('close')`, симметрично `reply.raw.off()`
  в `finally`.
- Тест: `apps/api/src/http/routes/plan-routes.test.ts`, блок «POST /api/plan по
  реальному сокету» — поднимает `app.listen({ port: 0 })` и ходит `fetch`; проверяет,
  что тело непустое, что событий больше одного и что поток начинается `plan.started`,
  а заканчивается `plan.ready`. Тест перепроверен на старом коде: с
  `request.raw.on('close')` он падает на `body.length > 0`.
- Живой прогон: `POST /api/plan` отдаёт 8 событий, 145 456 байт (live-режим),
  22 131 байт (fixture-режим).

  Применяется и к варианту, и к сегментам. Доменный `transportModeSchema` не менялся.

## P0-4. Маппинг полей теряет цену, длительность и перевозчика

`pick()` (`apps/api/src/adapters/inventory/mcp/fields.ts`) сравнивает **точное**
нормализованное имя. Реальные ответы MCP:

| Поле MCP | Что в нём | Что делает адаптер |
|---|---|---|
| `price` | объект `{amount, currency}` | `pickNumber` получает объект → **цена теряется** |
| `duration_min` | число | алиасов `durationmin` нет → **длительность теряется** |
| `carriers` | массив строк | алиас `carrier`, не `carriers` → **перевозчик теряется** |
| `segments_count` | число | алиаса нет → transferCount теряется |
| `departure_at` / `arrival_at` | ISO | ✅ читается |
| `legs[]` | массив | ✅ читается как segments |
| `checkout_url` | строка | ✅ читается |

То есть даже после починки P0-3 варианты придут без цены и длительности —
scoring и бюджетные фильтры работать не будут.

### Исправлено

Коммит «Достаю цену, длительность, перевозчика и число пересадок из ответа MCP».

- `pickMoney()` читает цену из вложенного объекта (`price.amount`, `price.currency`),
  плоское значение по-прежнему имеет приоритет; запасной путь — `fares.price_from`.
- Добавлен алиас `durationmin` для `duration_min`.
- `pickOperator()` берёт `carriers` (массив), несколько перевозчиков склеиваются
  через запятую.
- `segments_count` читается как источник `transferCount` с поправкой на семантику:
  пересадок на единицу меньше числа сегментов (`max(0, count - 1)`).
- Дополнительно: `legs[].segments[]` разворачиваются в плоский список сегментов.
  Нормализатор считает пересадки как `segments.length - 1`, а нога соответствует
  направлению, а не сегменту, — без разворачивания пересадок всегда получалось 0.
- Тесты: `map-offers.test.ts`, блок «реальный payload search_multitransport» на
  фикстуре `__fixtures__/tutu-multitransport.json` (реальный ответ MCP,
  Москва → СПб, 05.09.2026, три варианта): цена `1620.82 RUB`, `durationMinutes: 320`,
  `operator: 'ФПК'`, `transferCount: 0`, совпадение числа сегментов с `segments_count`,
  места и `checkout_url`.
- Живой прогон: цена и длительность есть у 59 вариантов из 59.

## P0-5. Discovery привязывает категории к справочным tool'ам

Реальный результат `pnpm mcp:inspect` на живом MCP:

```json
{"suburbanTrain":"search_etrain","flight":"search_avia","train":"search_rail",
 "bus":"get_bus_instructions","hotel":"get_hotels_instructions",
 "hotelReviews":"get_offer_details"}
```

- **`bus` → `get_bus_instructions`**: `search_bus` и `get_bus_instructions` дают
  одинаковый счёт 3, tie-break по имени по возрастанию выбирает справочник.
- **`hotel` → `get_hotels_instructions`**: у `search_hotels` в описании есть слово
  «review», а matcher отелей содержит `exclude: ['review','отзыв']` → счёт 0.
- `search_multitransport` не используется вообще, хотя это единственный tool,
  который отдаёт все виды транспорта одним запросом со сводкой `modes_summary`.
- При этом `describeCapabilities()` рапортует `bus: available` и `hotel: available` —
  пользователю показывается доступность, которой нет.

Правки: приоритет `search*` над `get*_instructions`, снять exclude «review» у
отелей, исключить `*_instructions` из кандидатов на инвентарь, добавить
`multitransport` как отдельную capability.

### Исправлено

Коммит «Привязываю категории к поисковым tool'ам, а не к справочникам».

- `tool-catalog.ts`: tool'ы с именем на `*_instructions` исключены из кандидатов на
  инвентарь и уходят в `unmatched`.
- У matcher'а отелей снят `exclude: ['review','отзыв']`.
- Добавлен флаг `prefersSearchTool`: при равном счёте выигрывает имя с `search`.
  У `hotelReviews` флага нет — отзывы отдаёт детализирующий tool, а не поиск.
- `search_multitransport` отдельной capability **не стал** — это отдельная задача,
  а не P0; сейчас он остаётся в `unmatched`.
- Причина недоступности стала конкретной: если для категории нашёлся только
  справочник, в `reasons` пишется «Найден только справочный MCP tool
  (*_instructions), поиска для категории нет». `describeCapabilities()` берёт статус
  из `bindings`, поэтому категория без поискового tool'а помечается `unavailable`
  с этой причиной (закрывает пункт про ложный `available`).
- Тесты: `tool-catalog.test.ts` — приоритет поиска над справочником, причина
  «только справочник», tie-break по `search` в имени.
- `pnpm mcp:inspect` на живом MCP: `flight→search_avia`, `train→search_rail`,
  `bus→search_bus`, `suburbanTrain→search_etrain`, `hotel→search_hotels`,
  `hotelReviews→get_offer_details`. Живой прогон: все шесть категорий
  `available`.

## P1. Не используются самые ценные поля MCP

Реальный ответ `search_multitransport` содержит ровно те сигналы, на которых
построена продуктовая идея, и ни один из них сейчас не доезжает до scoring:

| Поле | Что даёт продукту |
|---|---|
| `fares.refundable_count` / `changeable_count` / `count` | возвратность = финансовая устойчивость |
| `fares.seat_categories` | запас мест по классам (сидячий/плацкарт/купе/люкс) |
| `review_summary.rating` + `review_count` | надёжность перевозчика (⭐ 9.4, 69 отзывов) |
| `meta.modes_summary` | плотность альтернатив по каждой моде = основа «плана Б» |
| `checkout_ref.is_multi_pnr` | раздельные билеты — прямой риск срыва стыковки |
| `vehicle_meta` | премиальность/двухэтажность — комфорт |
