# MCP discovery spike — отчёт

**Дата прогона:** 2026-08-19
**Целевой endpoint:** `https://mcp.tutu.ru/mcp`
**Требование:** §11.1 системного дизайна — до реализации production-адаптера выполнить discovery.

## Итог

**Live MCP недостижим из среды разработки. Решение: `FixtureInventoryGateway` по умолчанию,
live-адаптер реализуется по спецификации MCP и остаётся непроверенным до успешного прогона.**

Это заранее предусмотренный §11.1 сценарий: «До успешного spike приложение работает через
`FixtureInventoryGateway` и показывает badge "Демо-данные"».

## Что проверялось

Пробник говорил на raw JSON-RPC поверх Streamable HTTP (POST, `accept: application/json,
text/event-stream`), перебирая версии протокола `2025-06-18`, `2025-03-26`, `2024-11-05`
и выполняя `initialize` → `notifications/initialized` → `tools/list`.

## Наблюдения

| Проверка | Результат |
|---|---|
| DNS `mcp.tutu.ru` | Резолвится: CNAME → `www-2.tutu.ru`, A → `178.248.234.61` |
| TCP/TLS `https://mcp.tutu.ru/mcp` | `fetch failed` на всех трёх версиях протокола |
| `curl https://www.tutu.ru/` | `http=000`, connection timed out после **300 s** |
| `curl https://178.248.234.61/ -k` (по IP, без SNI-имени) | connection timed out после 25 s |
| `curl https://registry.npmjs.org/react` | `http=200` за **2.7 s** |

## Интерпретация

1. Имя резолвится, значит DNS и публичная зона в порядке — endpoint существует как хост.
2. Соединение не устанавливается **ни по имени, ни по IP**, то есть это не проблема
   TLS/SNI, не HTTP-ошибка и не отказ авторизации MCP. Ответа от сервера нет вообще.
3. Общая исходящая сеть работает (npm registry отвечает за секунды), значит причина —
   недостижимость конкретно хостов ТуТу из этой сети (маршрутизация, firewall или
   гео-ограничение), а не сбой окружения.
4. Поэтому **никаких выводов о tool names, схемах, авторизации и версии протокола сделать
   нельзя**. Пункты §3.2 системного дизайна остаются неподтверждёнными в полном объёме.

## Что из этого следует для реализации

- `docs/mcp-tools.snapshot.json` **не создан** — записывать в него догадки запрещено §3.3.
- `TravelInventoryGateway` остаётся единственным доменным интерфейсом; live и fixture —
  две его реализации, переключаемые `INVENTORY_MODE`.
- Live-адаптер пишется против официального `@modelcontextprotocol/sdk` и **обязан**
  выполнять discovery в рантайме: маппинг логической capability на реальное имя tool
  строится из `tools/list`, а не хардкодится.
- Любая capability, не найденная в discovery, помечается недоступной. Приложение
  деградирует до доступных категорий, а не падает.
- Пока `mcp:inspect` не прошёл успешно, интерфейс показывает badge «Демо-данные».

## Как повторить

```bash
pnpm mcp:inspect                       # использует TUTU_MCP_URL из .env
TUTU_MCP_URL=https://mcp.tutu.ru/mcp pnpm mcp:inspect
```

Команда завершается non-zero кодом при невозможности установить соединение и сохраняет
sanitized snapshot в `docs/mcp-tools.snapshot.json` при успехе. Секреты, cookies и
персональные данные в snapshot не попадают.

## Что проверить при появлении доступа

1. Реальные tool names по каждой категории: самолёты, поезда, автобусы, электрички, отели.
2. Входные JSON Schema: обязательные поля, формат дат, формат мест (код станции? id? строка?).
3. Выходные поля: есть ли координаты, детализация пересадок, стабильные id вариантов, TTL/availability.
4. Требования авторизации и лимиты частоты/параллельности.
5. Возвращается ли checkout-URL и на каких хостах.

После успешного прогона обновить `docs/SPEC.md` §1.1 и снять допущение 1.
